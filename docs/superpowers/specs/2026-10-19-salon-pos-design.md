# แบบระบบหน้าจัดการและขายสินค้า/บริการร้านทำผม

วันที่: 19 ตุลาคม 2569

## 1. เป้าหมายและข้อกำหนดที่ยืนยันแล้ว

ผู้ใช้ต้องการต่อยอดโปรเจกต์เดิมสำหรับงานระบบ POS ที่อาจารย์กำหนด โดยต้องเห็นและ
ใช้งานหน้าลูกค้า พนักงาน สินค้า บริการ ขาย และรายงานได้จริงบนเว็บ ไม่ใช่เพียง
เตรียมตารางฐานข้อมูล ใช้ Laravel 12, PHP views, CSS และ JavaScript ธรรมดา
ไม่เพิ่ม Blade, Tailwind CSS, Alpine.js หรือ frontend framework

ใช้ฐานข้อมูลและข้อมูลเดิม ไม่สร้างโปรเจกต์ใหม่ ไม่ล้างฐานข้อมูลจริง
เก็บระบบเข้าสู่ระบบ โปรไฟล์ และการปิดใช้งานบัญชีที่ทำไว้แล้ว
งานนี้ไม่รวมการจัดทำรายงานเล่มหรือสไลด์ส่งอาจารย์

## 2. แนวทางที่เลือก

ใช้ Laravel Controllers และ Form Requests รับฟอร์มจากหน้า `.php`
แยกกติกาการขาย สต็อก และการคืนเงินไว้ใน Services ที่ทดสอบได้
ใช้ Models กำหนดความสัมพันธ์และชนิดข้อมูล ส่วน queries สำหรับรายงานแยกจากการบันทึกขาย
หน้าจอใช้ layout ร่วมกัน และ JavaScript เฉพาะตะกร้า การคำนวณตัวอย่าง และการยืนยัน
การบันทึกข้อมูล ทุกการคำนวณสำคัญทำซ้ำฝั่งเซิร์ฟเวอร์

แนวทางทางเลือกคือ API พร้อม JavaScript ควบคุมทั้งหน้า ซึ่งเพิ่มภาระการเรียนรู้
จึงไม่ใช้สำหรับงานนี้

## 3. หน้าตาและการนำทาง

- เมนูด้านข้างภาษาไทย: Dashboard, ลูกค้า, พนักงาน, สินค้า/สต็อก, บริการ, ขาย, รายงาน
- ส่วนหัวแสดงชื่อพนักงาน บทบาท โปรไฟล์ และออกจากระบบ
- หน้ารายการมีชื่อหน้า ช่องค้นหา ปุ่มเพิ่ม ตาราง และแบ่งหน้า
- หน้าเพิ่ม/แก้ไขแสดง label ข้อความผิดพลาดรายฟอร์ม ค่าเดิม และปุ่มกลับ
- ใช้โทนสีขาว น้ำเงิน เทา ตาม CSS เดิม พร้อมสถานะสำเร็จ เตือน และผิดพลาด
- จอเล็กยุบเมนูด้วยปุ่ม JavaScript ธรรมดา ตารางเลื่อนได้ตามแนวนอน
- เมื่อยังไม่มีข้อมูล แสดงคำอธิบายและปุ่มเพิ่มตามสิทธิ์ แทนตารางว่างที่ไม่มีคำแนะนำ
- เปลี่ยน `/` ให้พาผู้ที่เข้าสู่ระบบไป Dashboard; ผู้เยี่ยมชมยังเข้าสู่ระบบได้
- หน้าใบเสร็จมี CSS สำหรับพิมพ์ ซ่อนเมนูและปุ่มระหว่างพิมพ์

## 4. สิทธิ์ผู้ใช้และการตั้งค่าผู้ดูแล

| การทำงาน | admin | cashier | stylist |
|---|---|---|---|
| Dashboard | ภาพรวมร้าน | ยอดขายของตน | จำนวนบริการที่รับผิดชอบ |
| ลูกค้า | ดู/เพิ่ม/แก้ไข/ประวัติ | ดู/เพิ่ม/แก้ไข/ประวัติ | ไม่มีสิทธิ์ |
| พนักงาน | จัดการ | ไม่มีสิทธิ์ | ไม่มีสิทธิ์ |
| สินค้า | จัดการราคา ต้นทุน และสต็อก | ดูสินค้าที่เปิดขาย ราคา และจำนวนคงเหลือ | ไม่มีสิทธิ์ |
| บริการ | จัดการ | ดู | ดู |
| ขาย/ใบเสร็จ | สร้างและดูทุกบิล | สร้างและดูบิลของตน | ไม่มีสิทธิ์ |
| ยกเลิก/ยืนยันคืนเงิน | ทำได้ | ไม่มีสิทธิ์ | ไม่มีสิทธิ์ |
| รายงานร้าน | ทำได้ | ไม่มีสิทธิ์ | ไม่มีสิทธิ์ |
| โปรไฟล์ของตน | ทำได้ | ทำได้ | ทำได้ |

ตรวจสิทธิ์ทุก endpoint ทั้งอ่านและเขียน ไม่อาศัยการซ่อนเมนูอย่างเดียว
ข้อมูลต้นทุนไม่ถูกส่งไปหน้า cashier และไม่มีตัวเลือก role ในโปรไฟล์สาธารณะ

ปิดการสมัครพนักงานด้วยตนเองบนหน้าเว็บเมื่อเริ่มใช้งานระบบจัดการพนักงาน
ผู้ดูแลเพิ่มบัญชีจากหน้าพนักงานและตั้งรหัสผ่านเริ่มต้นให้เป็นรายบัญชี
เพิ่มคำสั่ง CLI `php artisan salon:admin` ที่ถามอีเมลและให้เลือกสร้างหรือยกระดับ
บัญชีตามอีเมลที่ระบุ เพื่อจัดเตรียม admin โดยไม่เดาว่าบัญชีเดิมคนไหนควรได้สิทธิ์
รหัสผ่านใหม่รับแบบซ่อนข้อความ ไม่เก็บรหัสผ่านลง source code หรือ README

ไม่ให้ผู้ดูแลลดสิทธิ์หรือปิดใช้งาน admin คนสุดท้ายที่ยัง active รวมถึงการปิดบัญชี
จากหน้าโปรไฟล์ การเปลี่ยนบทบาทหรือสถานะต้องล็อกบัญชี admin ที่เกี่ยวข้องก่อนตรวจ
บัญชีปิดใช้งานยังคงอยู่และเข้าสู่ระบบไม่ได้ตาม middleware เดิม

## 5. รายละเอียดแต่ละโมดูล

### 5.1 ลูกค้า

- รายการค้นหาจากชื่อหรือเบอร์โทร แบ่งหน้า
- เพิ่มและแก้ไขชื่อ/เบอร์โทร เบอร์ไม่ซ้ำ ความยาวไม่เกิน 15 ตัวอักษร
- หน้ารายละเอียดแสดงจำนวนครั้งที่มา วันที่ล่าสุด และประวัติบิล/รายการบริการ
- จำนวนครั้งและวันที่ล่าสุดแก้ด้วยขั้นตอนขาย/ยกเลิก ไม่รับค่าจากฟอร์มลูกค้า
- ประวัติที่ cashier เห็นแสดงรายการใช้บริการและยอด แต่ลิงก์ใบเสร็จเปิดได้เฉพาะบิลของตน
- ไม่เพิ่มการลบลูกค้า เพื่อรักษาประวัติเดิม

### 5.2 พนักงาน

- รายการค้นหาชื่อ อีเมล หรือบทบาท และกรอง active/inactive
- เพิ่ม/แก้ไขชื่อ อีเมล เบอร์โทร บทบาท อัตราคอมมิชชัน และสถานะ
- อีเมลไม่ซ้ำ อัตราคอมมิชชัน 0–100 รหัสผ่านใหม่อย่างน้อย 8 ตัวอักษรพร้อมยืนยัน
- การแก้ไขที่เว้นรหัสผ่านว่างคงรหัสเดิม
- ปิดใช้งานแทนลบ และตรวจเงื่อนไข admin คนสุดท้าย
- อัตราคอมมิชชันเป็นข้อมูลพนักงานเท่านั้น ยังไม่เพิ่มระบบจ่ายค่าคอมมิชชันย้อนหลัง

### 5.3 สินค้าและสต็อก

- ค้นหาชื่อ/SKU กรองเปิดขายและสินค้าใกล้หมด (`stock_qty <= min_stock`)
- จัดการ SKU ชื่อ ต้นทุน ราคาขาย หน่วย จุดเตือน และสถานะเปิดขาย
- จำนวนคงเหลือไม่ให้แก้ในฟอร์มข้อมูลสินค้า
- สินค้าใหม่มีสต็อกเริ่มต้น 0; รับเข้าผ่านฟอร์มรับสินค้า
- รับเข้าเป็นจำนวนเต็มบวก และปรับยอดเป็นจำนวนเต็มตั้งแต่ 0 ขึ้นไป โดยต้องระบุเหตุผล
- ทุกการเปลี่ยนสต็อกใช้ transaction ล็อก product แล้วบันทึก stock_movements พร้อม
  ผู้ทำรายการ จำนวนที่เปลี่ยน และยอดหลังทำรายการ
- รายการ `in`/`out` เก็บ qty เป็นจำนวนบวก ส่วน `adjust` เก็บผลต่างแบบมีเครื่องหมาย
- เปิดดูประวัติเคลื่อนไหวได้ และปิดขายแทนลบสินค้า

### 5.4 บริการ

- รายการค้นหาชื่อและประเภทบริการ เพิ่ม/แก้ไขราคา ระยะเวลา และสถานะ
- ประเภทใช้ enum เดิม: cut, wash, color, perm, straighten, treatment, other
- ราคาไม่ติดลบและไม่เกินขนาด decimal ของฐานข้อมูล ระยะเวลาเป็นจำนวนเต็มบวก
- ปิดใช้งานแทนลบ เพื่อรักษาบิลเก่า

### 5.5 ขายและชำระเงิน

- หน้าเลือกสินค้าที่เปิดขายและบริการที่เปิดใช้ พร้อมค้นหาและเพิ่มตะกร้า
- เลือกลูกค้าหรือขายแบบลูกค้าทั่วไป เลือกช่าง active ที่มีบทบาท stylist ให้รายการบริการ
- รายการบริการต้องระบุช่าง รายการสินค้าไม่มี stylist
- ปรับจำนวนเป็นจำนวนเต็มบวก/ลบรายการได้ และจำกัดจำนวนต่อรายการไม่เกิน 999
- แสดงราคาต่อหน่วย ยอดรวม ส่วนลด ยอดสุทธิ เงินรับ และเงินทอน
- รองรับหนึ่งวิธีชำระต่อบิล: cash, promptpay, transfer, card
- เงินสดต้องรับไม่น้อยกว่ายอดสุทธิ วิธีอื่นบันทึก received เท่ายอดสุทธิและ change เป็น 0
- วิธีที่ไม่ใช่เงินสดต้องกรอกเลขอ้างอิง ระบบนี้บันทึกการยืนยันโดยพนักงาน ไม่เชื่อมธนาคาร
- เลือกโปรโมชั่นที่เปิดใช้งานจากข้อมูลเดิมได้เมื่อเป็นลูกค้าสมาชิกและครบเงื่อนไข
  ใช้ได้หนึ่งโปรโมชั่นต่อบิล คำนวณจากยอดก่อนส่วนลด ปัดสองตำแหน่ง และไม่ลดเกินยอดบิล
- ไม่เปิดส่วนลดกำหนดเองในรอบนี้ เพื่อให้กติกายอดเงินตรวจสอบได้จากโปรโมชั่น
- ยังไม่เพิ่มอัตราสะสมหรือใช้แต้มใหม่ เพราะยังไม่มีเงื่อนไขธุรกิจที่ผู้ใช้กำหนด
  เก็บข้อมูลแต้มเดิมและใช้การย้อนแต้มของ cancellation service ตามรายการที่มีจริง
- หลังกดชำระสำเร็จพาไปใบเสร็จที่พิมพ์ได้ มีเลขบิล วันเวลา พนักงาน ลูกค้า
  รายการ ช่าง ยอดก่อนลด ส่วนลด ยอดสุทธิ วิธีรับเงิน เงินรับ และเงินทอน
- หน้ารายการบิลค้นเลขบิล กรองวันที่และสถานะได้ admin เห็นทั้งหมด cashier เห็นของตน

ขั้นตอน checkout ฝั่งเซิร์ฟเวอร์:

1. ตรวจผู้ขาย active และสิทธิ์ ตรวจ request และ checkout token
2. เริ่ม transaction สร้างบิลและล็อกบิล ลูกค้า และสินค้าตามลำดับ ID
3. โหลดราคาและสถานะจากฐานข้อมูล ตรวจช่าง สต็อก และรวมจำนวนสินค้าซ้ำก่อนตัดสต็อก
4. ใช้จำนวนเงินหน่วยสตางค์ในการคำนวณ ไม่เชื่อยอด/ราคา/ส่วนลดจากเบราว์เซอร์
5. สร้างรายการขายพร้อมชื่อและราคาขณะขาย ห้ามแก้ย้อนหลังจากราคาปัจจุบัน
6. ตัดสต็อกและเขียน `out` movement พร้อม sale_id ใน transaction เดียวกัน
7. ถ้ามีลูกค้า เพิ่ม total_visits ครั้งเดียวต่อบิล ตั้ง last_visit_at และ visit_counted=true
8. ตั้งสถานะ paid ภายใน transaction แล้วคำนวณโปรโมชั่นตามจำนวนครั้งรวมบิลปัจจุบัน
   บันทึกการใช้สิทธิ์ผ่าน service เดิม โดยยังไม่ commit ข้อมูล
9. บันทึก payment; หากขั้นตอนไหนล้มเหลวย้อนกลับทั้งบิล/สต็อก/จำนวนครั้งและสถานะ paid
10. การส่งซ้ำด้วย token เดิมให้กลับใบเสร็จเดิมสำหรับผู้ขายคนเดิม ไม่ขายหรือตัดสต็อกซ้ำ

ใช้ UUID เป็นเลขบิลที่ย่อให้เหมาะกับคอลัมน์ bill_no ความยาว 20 ตัวอักษร พร้อม unique constraint
เมื่อชนกันให้สร้างใหม่โดยไม่ทำรายการซ้ำ เพิ่ม sales.checkout_token แบบ nullable unique
เพื่อรองรับบิลเก่าที่ไม่มี token การชน token ต้องตรวจเจ้าของบิลก่อนคืนผลลัพธ์

### 5.6 ยกเลิกบิลและคืนเงิน

- admin ระบุเหตุผลจากหน้ารายละเอียดบิล เรียก SaleCancellationService ที่มีอยู่
- คงหลักประกันการคืนสต็อก/แต้ม/สิทธิ์โปรโมชั่นเพียงครั้งเดียว และไม่ลบหลักฐานเดิม
- เมื่อยกเลิกบิลที่รับเงิน สร้างรายการรอคืนเงินตามระบบเดิม
- หน้ารายละเอียดบิลแสดงสถานะรอคืนเงินและปุ่มยืนยันคืนแล้วสำหรับ admin
- การยืนยันต้องมีเลขอ้างอิงหรือหมายเหตุ รับยอดเต็มของรายการ refund ไม่รองรับคืนบางส่วน
- บันทึก completed_at และ completed_by ใน transaction พร้อมล็อก refund
- การกดยืนยันซ้ำไม่เปลี่ยนเวลา/ผู้ยืนยัน/ข้อมูลหลักฐานของครั้งแรก
- ไม่โอนเงินหรือสั่งคืนเงินกับผู้ให้บริการภายนอก

### 5.7 รายงานและ Dashboard

- admin กรองช่วงวันที่ เริ่มต้นวันนี้ถึงวันนี้ แสดงยอดสุทธิจากบิล paid จำนวนบิล
  ส่วนลด และยอดเฉลี่ยต่อบิล (เป็น 0 เมื่อไม่มีบิล)
- แสดงยอดแยกสินค้า/บริการจาก sale_items และยอดแยกวิธีชำระจาก payments
  สรุปสินค้า/บริการเป็นยอดก่อนส่วนลด เพื่อไม่อ้างการแบ่งส่วนลดที่ไม่ได้บันทึกไว้
- แยกจำนวนบิล cancelled และยอดรอคืนเงินออกจากรายได้
- รายการรอคืนเงินในช่วงรายงานอิงวันที่ยกเลิก ไม่ใช่วันที่ขาย
- ไม่ join payments กับ sale_items โดยตรงจนยอดเงินถูกนับซ้ำ
- กรองวันตาม Asia/Bangkok โดยแปลงขอบเขตวันให้สอดคล้องกับเวลาที่เก็บใน DB
- กำหนด timezone แอปเป็น Asia/Bangkok และใช้เวลาของแอปอย่างสม่ำเสมอสำหรับรายการใหม่
  ไม่แปลงเวลาของข้อมูลเก่าแบบเดา หากข้อมูลเดิมต่าง timezone ต้องตรวจสอบก่อนย้าย
- Dashboard admin สรุปวันนี้ พร้อมสินค้าใกล้หมดและบิลล่าสุด
- Dashboard cashier สรุปยอดและบิลวันนี้ของตน ไม่เห็นต้นทุนหรือยอดรวมทั้งร้าน
- Dashboard stylist แสดงรายการบริการที่ตนรับผิดชอบวันนี้และจำนวนรายการ

## 6. ข้อมูลและการเปลี่ยน schema

ใช้ตารางเดิมทั้งหมด รวม promotion_redemptions และ payment_refunds ที่เพิ่มแล้ว
เพิ่ม migration ใหม่เฉพาะ sales.checkout_token และ payment_refunds.completed_by
พร้อม down() ที่ย้อน schema ได้ บิลเก่าคงค่า token และ completed_by เป็น NULL

กำหนดความสัมพันธ์ User, Customer, Product, Service, Sale, SaleItem, Payment และ
StockMovement ตาม foreign keys โดย SaleItem เชื่อมสินค้า/บริการแบบ polymorphic เดิม
ไม่เพิ่ม abstractions แบบ generic CRUD ที่ทำให้นักศึกษาอ่านเส้นทางโค้ดยาก

## 7. การตรวจข้อมูลและข้อผิดพลาด

- ฟอร์มที่เปลี่ยนข้อมูลมี CSRF และใช้ HTTP method ให้ตรง Routes
- แสดงข้อความผิดพลาดภาษาไทยและเก็บค่าที่กรอกแล้ว ยกเว้นรหัสผ่าน
- escape ข้อมูลผู้ใช้ทุกจุดใน PHP views และในตะกร้าใช้ textContent แทน HTML จากชื่อสินค้า
- ทรัพยากรที่ไม่มีให้ 404 การข้ามสิทธิ์ให้ 403 ไม่แสดงรายละเอียดฐานข้อมูล
- ตรวจขอบเขตตัวเลขตามคอลัมน์เงิน decimal(10,2) และจำนวนเต็มของฐานข้อมูล
- แสดงข้อผิดพลาดเมื่อสินค้าไม่พอ ราคา/สถานะเปลี่ยน หรือโปรโมชั่นถูกใช้ไปแล้ว
  และให้ผู้ใช้แก้ตะกร้าได้โดยไม่เกิดบิลหรือการตัดสต็อกค้าง
- ตรวจวันที่เริ่มไม่เกินวันสิ้นสุด และใช้ query parameters ที่ผ่าน validation

## 8. การทดสอบและเกณฑ์ยอมรับ

เก็บชุดทดสอบเดิมที่ยังตรงพฤติกรรมใหม่ ปรับการทดสอบ registration ให้ตรงการปิดสมัครสาธารณะ
เพิ่ม Feature/Service tests สำหรับ:

1. สิทธิ์อ่าน/เขียนแต่ละบทบาท รวมเข้าถึง URL โดยตรงและบัญชี inactive
2. CRUD validation ลูกค้า/พนักงาน/สินค้า/บริการ และ admin คนสุดท้าย
3. รับเข้าและปรับสต็อกพร้อมประวัติและ rollback เมื่อไม่สำเร็จ
4. ขายสินค้าและบริการร่วมกัน ตรวจราคา ช่าง เงินทอน และบิลที่ไม่ระบุลูกค้า
5. การส่งชำระซ้ำ สินค้าเกินสต็อก การรวมสินค้าซ้ำ สินค้าปิดขาย และราคา client ปลอม
6. โปรโมชั่นครบจำนวนครั้งพอดี ไม่ครบ และใช้สิทธิ์ซ้ำ พร้อม rollback ทุกตาราง
7. ยกเลิกบิลและยืนยันคืนเงินจริงซ้ำโดยไม่เพิ่มรายการหรือเปลี่ยนหลักฐาน
8. รายงานขอบเขตวัน ไม่มีข้อมูล หลายรายการต่อบิล และไม่รวม cancelled ในรายได้
9. การแสดงผล PHP views รวมชื่อที่มี HTML และการพิมพ์ใบเสร็จ

ตรวจ syntax PHP/JavaScript และทดสอบหน้าเว็บจริงทั้งหน้ารายการ ฟอร์ม ตะกร้า ใบเสร็จ
และขนาดหน้าจอเล็ก เมื่อทำเสร็จต้องเปิดเมนูครบทุกโมดูลตามสิทธิ์และขายจากหน้าจอจน
บันทึกข้อมูลจริงได้ โดยฐานข้อมูลจริงไม่ถูกเติมบิลทดสอบหรือข้อมูลตัวอย่างอัตโนมัติ
ข้อมูลสาธิตเป็น seed แบบเลือกเรียกเอง ไม่ล้างข้อมูลที่มีอยู่

## 9. ลำดับการพัฒนาและขอบเขตส่งมอบ

พัฒนาตามลำดับ: สิทธิ์/เมนู/Models → ลูกค้า/พนักงาน → สินค้า/สต็อก/บริการ →
checkout/ใบเสร็จ → ยกเลิก/คืนเงิน → รายงาน/Dashboard → ทดสอบหน้าจอและคู่มือเริ่มใช้งาน

ส่งมอบโค้ดในโฟลเดอร์โปรเจกต์เดิม การทดสอบที่ผ่าน migrations และ README ที่บอก
การสร้าง admin เริ่มระบบ และใช้งานแต่ละเมนู ไม่มี deployment หรือการส่งข้อมูลให้บุคคลอื่น
โฟลเดอร์นี้ยังไม่เป็น Git repository จึงไม่สร้าง repository หรือ commit โดยอัตโนมัติ

ไม่รวมระบบนัดหมาย หลายสาขา ภาษีเต็มรูปแบบ เครื่องอ่านบาร์โค้ด การเชื่อมธนาคาร
ระบบจ่ายค่าคอมมิชชัน หรือระบบแต้มใหม่ในการพัฒนารอบนี้
